Section-Lazy Worldgen

Generate the overworld one 16×16×16 section at a time, only when something needs it. Send caves, bases and entities to a player only when that player could see them. One visibility service decides both.

The design in one paragraph. Keep Moonrise's column pipeline for the cheap, horizontal work (structures, biomes, surface estimate). Turn every section below the surface into a proxy: a single-value stone or deepslate section that costs a few bytes. A per-player visibility service walks the section graph from the player's eye and produces a potentially-visible set (PVS). Three consumers read that set: the section generator (make proxies real), the chunk sender (send hidden sections as filler), and the entity tracker (hide entities that fail a line-of-sight check). Simulation is untouched. Hidden caves still tick, farms still run.

Two questions, kept apart

Your follow-up turned one problem into two, and they need separate state.

QuestionScopeStateChanges when
Does this section's real content exist yet?Server-wide, one per sectionPROXY → GENERATING → LIVEOnce. A section never goes back to proxy.
Has this player been sent the real content?Per player, per sectionHIDDEN ↔ REVEALEDEvery time the player's PVS moves.

A LIVE section can still be HIDDEN for a player. That is the case for a cave someone else already explored, or a base behind 30 blocks of stone. A PROXY section is always HIDDEN, because there is nothing real to send.

Core data shapes

Everything else follows from these. Note what is missing. There is no NOISE state. Noise for a section is a pure function of seed, column plan and position, so the decorator recomputes or caches it instead of storing it.

// server-wide, lives on LevelChunk / NewChunkHolder
enum SectionGen : byte { PROXY, GENERATING, LIVE }
final class ColumnSections {
  byte[]  gen;          // one SectionGen per section (24 in the overworld)
  short[] connectivity; // 15 face-pair bits per LIVE section, like the client's VisibilitySet
}

record ColumnPlan(                      // built once in the column pipeline, never mutated
  ChunkPos pos,
  short[] preliminarySurface,           // 16×16
  int bandMinSection, int bandMaxSection,
  FeatureIndex features,                // per section Y: instances whose box touches it
  List<CarverStart> carvers,            // starts from the 17×17 chunk neighbourhood
  BlockState[] proxyFill)               // per section: stone, deepslate, or water below ocean floor

record FeatureInstance(int step, int index, ChunkPos origin, BoundingBox writeBox, BoundingBox readBox)
record SectionDemand(long sectionKey, Cause cause, int distance)
enum Cause { WRITE_BARRIER, BUBBLE, VISIBLE, PREFETCH, SPAWN_PROBE, API }   // priority order

// per player, owned by the visibility service thread
final class PlayerView {
  Long2IntOpenHashMap revealed;   // column key -> 24-bit mask of sections sent with real content
  LongOpenHashSet     pvs;        // current potentially-visible section keys
  IntOpenHashSet      shownEntities;
}

Why each part works the way it does

ColumnPlan

What
The column stages vanilla already runs before TERRAIN: structure starts, references, biomes. Add the preliminary surface and a feature index.
How
Run EMPTY to BIOMES unchanged. Sample preliminary surface from the noise router. Run feature placement (positions only) for features whose placement is pure, and bucket each instance by the sections its box touches.
Why
Structures and biomes reach across many chunks and are cheap. Splitting them per section would add cross-section waits for no saving.
Not
Adding skip flags to ChunkStatus. A column-wide status cannot say "half of me is real".

Surface band

What
Sections from one below the lowest surface point up to the build limit. Always generated with the column.
How
From preliminarySurface min/max, widened by the tallest feature reach in the biome set.
Why
Every player sees the surface, trees and sky. Making them lazy only adds latency. Heightmaps come from the band, so a proxy never affects them.
Not
Lazy surface. It would pop in at the horizon.

Proxy section

What
A LevelChunkSection with a single-value palette, plus real biomes from the plan.
How
Fill block from proxyFill. Light treats it as fully opaque. It has no block entities, no ticks, no entities.
Why
Gameplay code needs no special case to read it. Mobs path around it like stone, and fluids treat it as a wall. It encodes on the wire in a few bytes.
Not
Air proxies. The client would render holes into the void.

Section noise

What
Terrain for exactly one section, or any sub-box of one.
How
Your fork's NoiseBasedChunkGenerator.doFill already samples a DensityVolume(16, height, 16). Build the volume over the section's Y range instead. Aquifers and surface rules are positional functions, so they run on the same range. Carvers run with the section as the clip box, the same way vanilla clips them to a chunk.
Why
It is a pure function. That makes it cacheable, parallel, and safe to recompute after a crash.
Check
Generating 24 sections one by one must give the same blocks as one full-column fill, bit for bit.

Clipped feature replay

What
Decorate one section without decorating its neighbours.
How
Take every instance from the 3×3 columns' indexes whose writeBox touches S, in vanilla order (step, index, origin). Reseed with setFeatureSeed as vanilla does. Run it against a view where reads of S see S's in-progress state and reads elsewhere see neighbour noise. Commit writes inside S and drop the rest. Structure pieces already take a clip box in postProcess(…, BoundingBox chunkBB, …). Pass the section box.
Why
The only shared write target is S itself, so no locks are needed. The result depends on the seed, not on which section generated first.
Cost
A tree that spans two sections runs twice, and an ore blob runs up to eight times. Placement is cheap next to noise. Measure it.

Feature footprint registry

What
A table from feature type to a conservative write and read reach.
How
Ores take their size, geodes their radius, and EnvironmentScanPlacement its maximum scan steps. A datapack feature with no entry gets a column-wide reach.
Why
One table replaces per-feature branches in the scheduler. An unknown feature degrades to "materialize the column", which is slow but never wrong.

Demand queue + write barrier

What
The only door from PROXY to LIVE.
How
Section tasks go on Moonrise's prioritised executor. A write to a proxy (block break, explosion, piston, fluid, plugin setType) raises that task to blocking and waits, the same way a sync chunk load does. Generator threads never wait on tick threads, so parallel ticking cannot deadlock on it.
Why
A write is the one thing that must never land on fake content. Reads may see filler, and the filler behaves like stone.

Persistence

What
LIVE saves as normal. PROXY and GENERATING both save as a flagged section with no block data.
How
Add a swift:gen byte per section to the chunk NBT. Generation is pure, so a section that was mid-generation at a crash restarts and gives the same result.
Exit
A /swiftgen materialize <radius|all> command and an offline batch tool. Vanilla Paper would read a flagged section as air, so a world must be materialized before it leaves the fork.

Visibility service

This is the piece your follow-up made central. It answers one question per player: which sections could this player see in the next moment? Generation, block sending and entity tracking all read the same answer, so a cave cannot be generated but never sent, or sent while its zombies stay invisible.

This is the cave-culling search the vanilla client uses for rendering, run on the server against server-side content. The "never step back" rule is what keeps it close to line of sight.

Section connectivity

What
15 bits per section saying which pairs of its 6 faces are joined by non-occluding blocks.
How
Flood-fill the 4096 blocks using BlockState.canOcclude(), the same test the client uses. Run it when a section becomes LIVE, and again at most once per tick when blocks in it change.
Why
Bases count automatically. Glass, doors and open trapdoors leave faces open, and solid walls close them. A sealed base reads as one closed box.

Prefetch ring and prediction

What
One extra hop past the visible set, plus a search from where the eye will be.
How
Start a second search at eye + velocity × 0.5 s. An elytra at about 30 blocks per second moves about two sections in that time.
Why
Reveal must happen before the player could see the section. Otherwise they see a stone wall turn into a cave.

Chunk sender

What
Decides per section whether the packet carries real blocks or filler.
How
When a column is sent, any section not in the PVS is written as proxyFill. That hides caves, bases, ores and chests alike. When a section enters the PVS, send it in a section-blocks update, or resend the whole column if several sections changed in one tick. Hook in where Paper Anti-Xray already rewrites chunk packets.
Why
The vanilla client only accepts whole columns, so a hidden section still has to be sent as something. Single-value filler is the cheapest something.
Re-hide
Off by default. Once the client has a section, hiding it again costs bandwidth and stops nothing the player already saw. Turn on rehide-blocks if anti-ESP matters more than bandwidth.

Entity tracker

What
Hides entities, including players, that the viewer cannot see.
How
Two stages. If the entity's section is not in the PVS, it is hidden with no further check. If it is, cast a few rays from the eye to the corners of its bounding box through cached LIVE blocks on the visibility thread. Show on first hit. Hide after about one second of misses, so an entity does not flicker at an edge.
Why
The PVS is coarse. A whole connected cave counts as visible, so a mob behind a pillar in it needs the finer test. Rays are cheap when they only run for entities that pass the coarse stage.
Also
Drop sound and particle packets whose source is in a hidden section. Otherwise footsteps give the base away.

Do you need ray tracing?

For generation and blocks, no. For entities, yes.
  • Generation. A ray cannot cross a section that has not been generated yet, because there is nothing to test it against. A ray-based design ends up generating the frontier and then testing it, which is the graph search with more work.
  • Blocks. Rays are samples. A one-block cave mouth can fall between two of them and show up as a stone patch. The graph search is conservative, so it never misses an opening. Its cost is per section change, not per player per frame.
  • Entities. Here the graph is too coarse, and the work is small (few rays, only for entities that pass the PVS check). That is the job rays are good at.

Where the time goes, and what it saves

The overworld has 24 sections from Y −64 to 320. Your fork's fill samples density for the whole height of every column. The surface band is usually 4 to 8 sections, and the sky above it is cheap to fill. The biggest share left is the 8 to 10 sections of solid underground that nobody near the column ever sees (guess, not measured).

The win is largest where players load far more columns than they go under, such as elytra travel, high view distance and the outer view-distance ring outside spawn range. It is smallest in a base area where everything nearby ends up generated anyway. Phase 0 has to replace these guesses with numbers before any later phase is judged.

Build order

Each phase lands as Paper patches on its own branch off swift, behind one config switch, and ends in a check you can rerun.

P0

Measure first. A run-bench scenario that generates a fixed seed and region and reports ms per column per stage (noise, surface, carvers, features, light), plus bytes sent per player. Without it no later phase can claim a win.

P1

Section-ranged noise. DensityVolume per section. Check: 24 section fills match one column fill, bit for bit, over 10,000 columns.

P2

Proxy, write barrier, persistence. First version: the first demand on a column materializes its whole remainder with vanilla decoration. That proves the state machine, saving, reload, the blocking path and the client resend before per-section features exist. Check: fake-player GameTests that dig, blow up and flood into proxies and find real blocks, plus a restart mid-generation.

P3

Visibility service and chunk sender. Connectivity, BFS and filler for hidden sections, so caves and bases are hidden from players before generation turns lazy. Check: a fake player on the surface receives filler for a sealed base 20 blocks down. After it digs in, it receives real blocks before it reaches them.

P4

Entity culling. PVS check, rays and hysteresis, plus the sound and particle filter. Check: a hidden mob in a sealed room is never tracked. A mob in view is tracked within one tick.

P5

Per-section decoration. Feature index, footprint registry and clipped replay. Replaces P2's whole-column materialize. Check: generating sections in random orders gives the same result. Diff against vanilla ores and report the share of blocks that differ.

P6

Demand from visibility, spawn probes, materialize command. Then rerun P0 and compare.
